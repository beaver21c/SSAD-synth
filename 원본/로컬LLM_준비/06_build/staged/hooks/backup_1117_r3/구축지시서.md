## 0. 전제와 지킬 사항

- 모형에는 분석 자료를 넣지 않음. 조립기가 모형에 보내는 것은 질문, 참고 자료, 집계 결과의 표준 출력뿐이며 이 구조를 바꾸지 않음
- 추론 서버는 `127.0.0.1`에서만 듣게 함. 외부 주소(API)를 설정 파일에 넣지 않음
- 모형을 올리기 전에 GPU 점유를 확인함. 다른 작업이 GPU를 쓰는 동안에는 모형을 올리지 않음(기동 스크립트와 일괄 실행 스크립트가 4GB 넘게 점유돼 있으면 중단함)
- 「결정필요사항.md」의 1~3번(추론 경로와 양자화 수준, 미세조정 여부, GPU 사용 시간대)이 정해지지 않았으면 기본값(경로 나를 먼저 시도하고 뜨지 않으면 경로 가, 미세조정 없음)으로 5단계까지만 진행하고 결과를 보고함
- 각 단계를 마치면 `python 06_build/preflight.py --quick`으로 `현황.json`을 갱신함

- 경로 가의 가속 라이브러리(flash-linear-attention, causal-conv1d)는 설치하지 않았음. 설치하면 transformers가 선형 주의 층의 정규화 모듈을 다른 구현으로 바꾸고 생성 시점의 GPU에 두는데, GPU 2장 분할과 함께 쓴 이력이 없고 GPU 없이는 확인할 수 없음. 이 PC의 기존 학습(Qwen3.8-27B)도 이 라이브러리 없이 수행됐음
- 경로 다: 양자화본이 `lm_head`까지 양자화한 경우 vLLM 0.20.2가 읽지 못한 기록이 있음(`/mnt/share/corpus/docs/멀티모델_채팅서버_2026-08-20.md`)

## 4단계. 서버 기동과 연결 확인 (GPU 필요)

GPU가 비어 있을 때 수행함. 2026-11-16에 이 절차로 GPU에서 수행함(Q5_K_M: 적재 190초, GPU0 9.9GiB·GPU1 10.1GiB, 생성 초당 20.1토큰, 입력 처리 초당 약 1,000토큰).

긴 작업은 반드시 `launch_job.sh`로 띄움. 작업이 이 창(세션)과 분리된 단위로 실행되고 메모리 압력 감시가 함께 붙음(사유는 아래 「문제와 대처」의 메모리 압력 항목).

```bash
bash 06_build/launch_job.sh eval bash 06_build/run_pipeline_eval.sh          # 평가 단계 전체(Q5_K_M 평가 2회 → Q4_K_M → Q6_K)를 이어서 수행
bash 06_build/launch_job.sh finetune bash 06_build/run_pipeline_finetune.sh  # 미세조정 단계 전체(스모크 → 학습 → 병합 → 변환 → 평가). 평가 단계가 끝나기를 기다렸다가 시작함
bash 06_build/launch_job.sh gpuday bash 06_build/run_gpu_day.sh              # 4단계와 5단계 한 차례만
tail -f logs/pipeline/pipeline.log                                           # 진행 상황(단계별 시작·끝)
systemctl --user stop <단위 이름>.scope                                       # 중지(단위 이름은 launch_job.sh 가 출력함)
```

아래 한 줄이 4단계와 5단계를 이어서 수행함(위의 `launch_job.sh`로 감싸 실행함).

```bash
bash 06_build/run_gpu_day.sh                       # 경로 나(Q5_K_M)를 먼저 시도, 뜨지 않으면 경로 가
bash 06_build/run_gpu_day.sh --skip-eval           # 연결 확인까지만
bash 06_build/run_gpu_day.sh --path transformers   # 경로 가로 지정
bash 06_build/run_gpu_day.sh --quant Q4_K_M        # 다른 양자화 수준
```

- 수행 순서: GPU 점유 확인(4GB 넘으면 중단) → 서버 기동과 응답 대기 → 적재 후 GPU 메모리 기록 → 연결 확인 질문 4개 → 평가 2회(유사 예시 0개, 2개) → 요약 → 서버 종료
- 기록: `logs/gpu_day/<시각>/`의 `summary.md`(요약), `check_1~4.txt`(연결 확인 질문의 전체 출력), `server_*.log`(서버 기록), `eval_*.log`
- 중간에 끊기면 같은 명령을 다시 실행함. 평가는 끝난 문항을 건너뛰고 이어서 수행함

- 사고 과정 출력: 경로 나는 서버 인자 `--reasoning off`로, 경로 가는 설정 파일의 `extra_body`로 끔. 이 모형의 대화 틀은 끄지 않으면 사고 과정을 켜고 시스템 문구 앞에 영어 안내문을 붙임. 응답에 `</think>`가 섞이면 끄기가 적용되지 않은 것이며 일괄 실행 스크립트가 요약에 주의를 적음

## 5단계. 평가(미세조정 없음, GPU 필요)

`run_gpu_day.sh`가 아래 두 실행을 이어서 수행함. 따로 돌릴 때는 서버를 띄운 상태에서 실행함.

- 산출: `05_eval/runs/<이름>/report.md`(지표·기준 대조·미통과 문항), `transcripts.jsonl`(대화 기록), `run_meta.json`(소요 시간, 토큰 수, 오류 문항)
- 판정: `05_eval/criteria.json`의 기준(안)을 모두 충족하면 7단계로, 미달이면 6단계로 감. 작업 방식의 준수는 수치 근거율(98% 이상), 검증 경고 잔존율(5% 이하), 변수 근거율(95% 이상)로, 제도 용어의 처리는 제도 용어 문항 통과율(80% 이상)과 첫 질문에서 되물은 비율로 봄. `report.md`의 「검증 단계의 개입 내역」에서 응답을 다시 쓰게 한 문항 수와 경고가 뜬 문항 수를 확인함. 「차단 실패 건수」가 0이 아니면 즉시 중단하고 `ssda/guard.py`·`runner.py`를 점검함
- 문항 하나에서 서버 오류가 나면 한 번 다시 시도하고, 그래도 실패하면 그 문항만 `errors.jsonl`에 남기고 계속함. 오류 문항이 남으면 종료 코드 2로 끝나고 `report.md`에 「미완료」가 표시됨. `--resume`으로 다시 실행하면 남은 문항만 수행함
- 양자화 수준 비교가 필요하면 `--quant Q4_K_M`·`--quant Q6_K`로 같은 평가를 돌리고 `산출값 일치율`과 소요 시간(`run_meta.json`)을 비교함
- GPU 실측(2026-11-15~17): 평가 1회(161문항)에 공식 가중치 54~65분, 미세조정 모형 38~40분. 입력 토큰은 처음 판 프롬프트 115만~134만, 개선판 2 153만~166만, 개선판 3 172만, 짧은 판 70만 개임
- 아래는 GPU 사용 전의 어림임. 토큰 수는 실제 양자화본(Q4_K_M)을 CPU로 구동해 12문항에서 잰 값이 있음(2026-11-15): 문항당 모형 호출 1.8회, 출력 약 390토큰, 입력 처리 약 3,800토큰. 161문항으로 환산하면 평가 1회에 출력 약 6.3만 토큰, 입력 약 62만 토큰임
- 소요 어림(GPU 속도는 가정): 생성 속도 초당 15토큰, 입력 처리 초당 500토큰이면 평가 1회에 약 1시간 35분(유사 예시 2개를 넣으면 약 1시간 45분), 기본 일괄 실행(평가 2회)에 약 3시간 30분이 걸림. 생성 속도가 초당 8토큰이면 평가 1회 약 3시간, 초당 25토큰이면 약 1시간임. 범위별 소요는 `결정필요사항.md` 3번의 표에 있음. 실제 속도는 4단계의 서버 기록과 `summary.md`에서 확인함
- llama.cpp는 이 모형 구조에서 프롬프트 앞부분을 임의 위치부터 이어 쓰지 못해, 질문이 바뀌면 시스템 프롬프트를 처음부터 다시 처리함(CPU 구동 기록에서 13문항 모두 전체 재처리). 조립기가 시작할 때 시스템 프롬프트만 담은 예열 요청을 한 번 보내 서버에 상태 저장 지점을 남기게 했음(`clients.py`의 `warmup`, 설정 `prompt.warmup`으로 끌 수 있음). 효과는 `모형반입/cpu_실모형_시험.md`의 「하네스 보완 후 재확인」에 기록함

## 6단계. 보강(기준 미달 시에만, 아래 순서로)

1. **미통과 문항 분석**: `report.json`의 `failed_items`를 `transcripts.jsonl`에서 찾아 원인을 분류함(변수 선택 오류, 조건식 오류, 형식 미준수, 통제 위반 코드 작성, 검증 경고 미대처, 근거 없는 수치 등). 문항별 `verification` 항목에 경고·주의, 정의를 보지 않은 변수, 대조에 걸린 수치가 기록돼 있음
   - 자동 점검이 잡지 못한 실수 유형이 반복되면 `작업방식_이식안내.md` 8절의 순서로 점검 규칙·검증 요령·학습 예시·평가 문항을 추가함
2. **지식 자료·프롬프트 보강**: 반복되는 오류는 `01_knowledge/docs/analysis_recipes.md` 등에 요령으로 적고 `build_knowledge.py` → `retriever.py build` 후 다시 평가함. 시스템 프롬프트를 고치면 `system_prompt_short.md`도 함께 고치고 학습 자료를 다시 생성함
3. **유사 예시 삽입**: `config/assistant.yaml`의 `prompt.n_examples`를 1~3으로 올림. 예시는 학습 분할에서만 뽑히므로 벤치마크 문항과 겹치지 않음
4. **제도 용어 사전 보강**: 제도 용어 문항이나 대화 기록에서 풀이하지 못한 약어, 되묻지 않아도 되는데 되물은 질문이 나오면 `01_knowledge/programs/glossary.yaml`에 약어나 `resolvers`를 추가하고 `programs/README.md` 6절의 순서로 다시 만듦
5. **미세조정**: 「결정필요사항.md」 2번에서 수행하기로 정한 경우에만 함
   - `06_build/finetune_lora.py --check-data`로 학습 자료 점검
   - 실행 환경은 conda 환경 vllm(이 PC에서 Qwen3.8-27B 코퍼스 학습이 완주한 환경). `conda activate vllm && python 06_build/finetune_lora.py --smoke`로 적재·LoRA 부착·역전파를 먼저 확인함. 적재·분할은 완주한 스크립트에서 옮긴 것이고, 학습 루프 전체(응답 구간 손실, 체크포인트 저장·재개, 어댑터 저장)는 구조가 같은 축소 모형과 실제 학습 자료(1,536토큰 상한)로 CPU에서 끝까지 실행해 확인했음. 27B 원본에서는 길이 상한 1,536토큰, 분할 위치 34로 완주함(2026-11-16: 1,179건 3에폭 884스텝, 7.8시간, GPU 최고 12.8·12.0GiB, 건너뛴 예시 없음)
   - 메모리가 부족하면 부족한 GPU 쪽의 층이 줄도록 `--split-at`을 옮기거나(기본 34) `--max-len`을 낮춤. 일괄 스크립트(`run_pipeline_finetune.sh`)는 스모크 시험에서 분할 위치와 길이 상한을 차례로 바꿔 가며 정함. 참고 자료를 넣은 판(`--context full`)은 평균 2,600토큰이어서 이 PC에서는 권하지 않음
   - 기반 모형이 Qwen/Qwen3.8-27B이면 `--init-adapter /mnt/share/corpus/models/adapters/chat_corpus_qwen_v1`로 코퍼스 어댑터에서 이어서 학습할 수 있음(결정필요사항 11번)
   - 학습한 어댑터를 쓰는 방법은 두 가지임
     - 경로 가: 어댑터를 그대로 붙임. `bash 06_build/run_gpu_day.sh --lora <어댑터 폴더>` 또는 `python 06_build/serve_transformers.py --lora <어댑터 폴더>`
     - 경로 나: llama.cpp의 어댑터 변환 도구(`convert_lora_to_gguf.py`, 2026-05-21 판)는 이 구조의 선형 주의 층 어댑터를 변환하지 못함(축소 모형으로 확인). 어댑터를 기반 가중치에 합친 뒤 다시 변환함: `python 06_build/merge_lora.py --base <공식 가중치 폴더> --adapter <어댑터 폴더> --out <출력 폴더>` → `SNAP=<출력 폴더> NAME=Arete-27B-lora bash 06_build/make_gguf.sh Q5_K_M`. 합치는 계산은 축소 모형에서 PEFT의 병합 결과와 같음을 확인했고 27B 원본에 적용함(2026-11-16: 병합 15분, 변환·양자화 36분, `Arete-27B-lora-Q5_K_M.gguf`)(출력 약 55GB, CPU)
   - 미세조정한 모형에는 `prompt.system`을 개선판 3(`03_prompts/system_prompt_v3.md`)으로 둠. 평가에서 학습 자료와 같은 문구인 짧은 판(121문항 중 108문항)보다 개선판 2(115문항)의 통과가 많았고, 처음 판(102문항)은 확인 요청이 다시 늘어남. 보완본(분석 함수 0.4.1)을 반영한 뒤의 재평가에서는 개선판 2가 117문항, 개선판 3이 118문항이고, 보류 검증 문항 1·2차를 합한 213문항 기준으로 개선판 3(203문항)이 개선판 2(200문항)보다 많음
   - `eval_run.py --name arete27b_q5_lora --resume`로 다시 평가하고 미세조정 전 결과와 비교함

## 8단계. 실제 자료로 전환(폐쇄망 안에서 수행)

1. `SSDA_DATA`를 실제 분석 자료(parquet)로 바꿈. `ssda`는 자료 전체를 메모리에 올리므로 자료 크기와 RAM을 먼저 대조하고, 부족하면 `ssda/core.py`의 `open_data`를 필요한 열만 읽는 방식으로 고침
2. `01_knowledge/build_knowledge.py`의 자료 경로(`DATA`)를 바꿔 다시 실행함(변수별 값 유무·범주 수 갱신) → `programs/build_glossary.py`(제도 용어 사전의 변수 대조. 실제 자료에 없는 변수가 있으면 중단되므로 사전을 먼저 맞춤) → `retriever.py build`
3. 민감도 등급 분류(`build_knowledge.py`의 `grade`)와 최소 관측 수·분류 기준 수(`ssda/core.py`의 `THR`, `MAXDIM`), 자동 점검의 기준값(`ssda/verify.py`: 분모 15%·300건, 분류 누락 0.5%, 0 포함 20%)을 운영 주체가 확정한 기준으로 맞춤
   - 분모 점검은 연령대별 해당자 유무를 쓰므로 실제 자료에서 경고가 과하거나 부족하지 않은지 벤치마크 정답 코드로 먼저 확인함(`build_benchmark.py`가 정답 코드에 남는 경고를 출력함)
4. `05_eval/build_benchmark.py`를 다시 실행해 정답 산출값을 갱신하고 5단계 평가를 다시 돌림
5. 학습 자료를 쓰는 경우 `04_training/generate.py`·`validate.py`를 다시 실행함. 실제 자료에서 만든 학습·평가 자료에는 실제 집계값이 들어가므로 폐쇄망 밖으로 내보내지 않음

폐쇄망 반입 목록: 이 준비 폴더, 모형 파일(해시 기록 포함), `llama-server` 실행 파일 또는 원본, `requirements-serve.txt`의 wheel, (미세조정 시) `requirements-train.txt`의 wheel과 모형 원본

| 증상 | 확인할 곳 | 대처 |
|---|---|---|
| 서버 적재 중 메모리 부족 | `nvidia-smi` 점유, 서버 기록 | 다른 GPU 작업 종료, `CTX` 축소, 더 낮은 양자화 |
| llama.cpp 서버가 GPU에서 뜨지 않음 | `logs/gpu_day/<시각>/server_gguf.log` | 일괄 실행 스크립트가 경로 가로 바꿔 다시 시도함. 원인이 llama.cpp 판이면 최신 판으로 올려 `build_llamacpp.sh cuda`를 다시 실행 |
| 서버가 500(Failed to parse input)을 돌려줌 | `run_meta.json`의 `raw_fallbacks` | 출력에 온전하지 않은 글자가 섞인 경우임. 모형 연결부가 원문 생성으로 다시 받으므로 조치 불필요. 잦으면 `max_tokens`가 응답 중간에 걸리는지 확인 |
| 평가가 중간에 끊김 | `05_eval/runs/<이름>/errors.jsonl` | 같은 명령을 `--resume`으로 다시 실행 |
| 작업과 Claude 앱이 함께 사라짐 | `journalctl --since "1 hour ago" \| grep oomd`, `oomctl` | 메모리 부족이 아니라 메모리 압력 감시(systemd-oomd: 세션의 압력 50%가 20초 넘게 지속)에 의한 종료임. 2026-11-15 13:31에 17.9GiB 양자화본을 HDD에서 메모리 매핑으로 올리던 중 발생함(압력 72%, RAM은 26GB 남음). `serve_llamacpp.sh`는 직접 읽기(`--no-mmap --direct-io`)로 올리고, 긴 작업은 `launch_job.sh`로 띄워 압력 감시(`psi_guard.py`)를 붙임. 메모리 상한을 낮추는 것은 해결책이 아님 |
| 모형을 올리는 중에 평가가 시작돼 모든 문항이 503 오류 | `run.log`의 서버 응답 확인 시각, `errors.jsonl` | 서버가 적재 중에 돌려주는 503을 기동 완료로 본 것임(2026-11-15 첫 기동). `run_gpu_day.sh`의 판정을 고쳤고 모형 연결부가 「적재 중」 응답에는 최대 15분 기다림. 오류만 남은 평가 폴더는 지우고 다시 실행 |
| 변환·양자화가 「죽었음」으로 끝남 | `모형반입/gguf_build.log`, `free -g` | 메모리 상한에 걸린 것임. RAM 여유가 13GB 이상일 때 다시 실행(이미 만든 파일은 건너뜀) |
| 응답이 `<think>`로 시작하거나 매우 느림 | 서버 기동 인자, `extra_body` | 사고 과정 끄기 인자 적용 |
| 코드 블록 없이 설명만 답함 | `transcripts.jsonl` | 시스템 프롬프트를 `system_prompt.md`(긴 판)로, `n_examples` 2로 |
| 없는 변수명을 씀 | 미통과 문항의 `context_ids` | `n_variable_cards` 증가, 변수 카드 문구 보강 |
| 약어·통칭을 풀이하지 못함 | 대화 기록의 참고 자료에 「제도 설명」 카드가 있는지 | 제도 용어 사전에 약어 추가 |
| 되물어야 할 용어를 임의로 해석해 산출 | 검증 요약의 「용어」 줄, `첫 질문에서 되물은 비율` | 시스템 프롬프트의 「제도 용어」 절을 앞쪽으로, `n_examples`를 올려 F30 유형 예시가 들어가게 함 |
| 되묻지 않아도 되는 질문을 되물음 | 대화 기록의 「용어 확인」 카드 | 사전의 `resolvers`에 그 낱말 추가 |
| 같은 오류를 반복해 실행 횟수 소진 | 실행 결과의 오류 문구 | `ssda`의 오류 문구에 고치는 방법을 더 구체적으로 적음 |
| 함수의 인자 이름·순서를 틀리게 씀(`TypeError`) | 대화 기록의 [실행 결과]에 「사용법:」 줄이 붙었는지 | 실행기가 인자 오류에 함수 서명을 돌려줌(`runner.usage_hint`). 같은 함수에서 반복되면 시스템 프롬프트의 「함수 사용법」에 그 함수의 예를 더함 |
| `QueryError: 항목 이름 … 이 구간과 맞지 않음` | 대화 기록의 `define_group` 호출 | 구간 이름과 경계를 대조하는 점검에 걸린 것임(이름이 한 칸씩 밀린 표를 막음). 모형이 고치지 못하고 반복하면 시스템 프롬프트의 「함수 사용법」 예를 보강. 줄여 적은 단위 때문에 옳은 이름이 걸리면 `core.py`의 `_check_labels` 제외 조건에 그 표기를 더함 |
| 변수 안내·제도 설명에 「결과」 문단이 없음 | `응답 형식 준수율`, 대화 기록 | 시스템 프롬프트의 「응답 형식」에 코드 없이 답하는 경우의 형식이 있는지 확인 |
| 질문마다 입력 처리가 길게 걸림 | 서버 기록의 `forcing full prompt re-processing` 횟수 | 예열 요청(`prompt.warmup`)이 켜져 있는지, 서버 기록에 `restored context checkpoint`가 나오는지 확인 |
| `산출값 일치율`만 낮음 | 정답 코드와 모형 코드 비교 | 분모(where) 누락·`_yn1`/`_yn2` 혼동 여부 확인 후 분석 요령 보강 |
| 검증 경고를 읽고도 고치지 않음 | `검증 경고 잔존율`, 대화 기록 | 시스템 프롬프트를 긴 판으로, `n_examples`를 올려 F27 유형 예시가 들어가게 함. 그래도 남으면 미세조정 검토 |
| 응답을 다시 쓰게 하는 일이 잦음 | `report.md`의 개입 내역 | 수치를 어림해 적는 경향임. 「결과」 작성 규칙을 시스템 프롬프트 앞쪽으로 옮기고 예시를 늘림 |
| 수치 대조가 옳은 수치를 걸러냄 | 대화 기록의 `ungrounded_numbers` | 단위 환산이 원인이면 `verify.ground_numbers`의 환산 규칙에 추가 |
