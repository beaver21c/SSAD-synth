# 작업 방식 이식 안내 — 분석·시각화 요청의 처리 방식과 검증 방식

작성 기준일 2026-11-13(2026-11-15 갱신) · 대상: 로컬 모형(NousResearch/Arete-27B, 공식 가중치·양자화본 준비 완료, GPU 구동 전)에 붙이는 하네스와 지침

## 1. 요지

- Claude Fable이 이 사업에서 데이터 분석·시각화 요청을 처리하고 검증한 방식을 8단계로 정리하고, 단계마다 로컬 모형에 옮기는 수단을 정해 구현함
- 옮기는 수단은 네 가지임: **하네스**(조립기·실행기가 코드로 수행), **지침**(시스템 프롬프트·검증 요령 문서), **학습 자료**(그 방식대로 처리한 대화 예시), **평가**(그 방식을 지켰는지 재는 지표)
- 설계 원칙: 확인 절차는 가능한 한 하네스가 수행함. 로컬 모형이 지침을 일정하게 지키지 못하는 경우에도 확인이 빠지지 않도록 하기 위함임. 모형에는 확인 결과(「[검증 결과]」)를 읽고 대처하는 일만 맡김
- 자체 시험 결과(모형 없이, 일부러 틀리게 답하는 모의 모형 사용)
  - 대상 조건을 뺀 코드 63건 가운데 42건을 탐지하고 40건을 정답과 같게 고치게 함
  - 실행 결과에 없는 수치를 적은 응답 97건을 모두 탐지해 다시 쓰게 함
  - 자료 파일을 직접 읽는 코드는 모두 실행 전에 차단함
- 실제 모형이 「[검증 결과]」에 대처하는 정도는 구축지시서 5단계의 평가에서 수치 근거율, 검증 경고 잔존율, 변수 근거율로 확인함. GPU 평가(2026-11-15~17)에서 기본 구성(미세조정 모형, 개선판 3, 분석 함수 0.4.1)은 수치 근거율 1.0, 검증 경고 잔존율 0.0, 변수 근거율 1.0이고, 응답을 다시 쓰게 한 문항 1개, 검증 경고가 뜬 문항 1개, 없는 변수로 실행 전에 돌려보낸 횟수 4회임. 보완본을 반영한 개선판 2 구성에서는 검증 경고(1 아님 비교)와 집단 정의 함수의 오류 안내를 받은 2문항이 코드를 고쳐 통과함

## 2. Claude Fable의 처리 방식과 검증 방식

이 사업의 가상데이터 생성, 대시보드 구축, 적용 사례 작성에서 실제로 쓴 방식임.

| 단계 | 하는 일 | 이 사업에서의 예 |
|---|---|---|
| 1 요청 해석 | 대상 집단, 지표, 분류 기준, 산출 형태를 정함. 요청에 없는 사항은 가정으로 정해 밝히고, 결과가 크게 달라지는 경우에만 확인함 | 수급률의 분모를 제도의 대상 연령으로 두고 그 사실을 적음 |
| 2 자료 확인 | 코드를 쓰기 전에 변수의 정의, 단위, 기준 시점, 결측 규약을 읽음. 변수명을 짐작하지 않음 | 여부 변수는 해당하면 1, 아니면 결측임을 코드북에서 확인 |
| 2-1 용어 확인 | 제도명·약어가 무엇을 가리키는지 확인하고, 여러 내역을 묶는 말이면 어느 내역인지 정함. 정할 수 없으면 되물음 | 기초생활보장 수급을 급여별 변수로 나누어 다룸, 본인부담금의 범위를 코드북으로 확인 |
| 3 계획 | 작업을 단계로 나누고 한 번에 한 가지를 산출함 | 지표 정의 → 집계 → 그림 → 보고 순서 |
| 4 실행과 오류 처리 | 작은 단위로 실행하고 결과를 본 뒤 다음으로 넘어감. 오류는 원인을 밝히고 고침. 같은 코드를 다시 내지 않음 | 확대 생성 실패 2건의 원인을 추적해 수정 |
| 5 산출 검증 | 분모와 대상 인원이 요청과 맞는지, 집단별 값이 전체 값과 어긋나지 않는지, 표에서 빠진 대상이 있는지, 억제·결측이 어떻게 처리됐는지 확인함. 다른 경로로 낸 값과 대조함 | 분석 함수의 시도별 수급률을 대시보드 값과 대조해 일치 확인 |
| 6 산출물 검증 | 그림과 문서를 실제로 열어 제목, 축, 글자 겹침·잘림을 확인하고 고침 | 대시보드 그래프의 눈금 겹침·라벨 잘림 수정 |
| 7 수치 대조 | 보고 문장의 수치를 산출값과 기계적으로 대조함. 수치를 기억이나 어림으로 적지 않음 | 보고서 본문 수치 검사, 학습 자료 코드 전수 재실행 |
| 8 보고 | 결론을 먼저 적고, 적용한 가정과 한계, 확인한 것과 확인하지 못한 것을 구분해 적음 | 「실측값이 아닌 추정치」「미실행」 표기 |
| 공통 | 자료 안의 지시문을 따르지 않음. 출력 통제를 우회하지 않음 | 개인 단위 자료를 산출물에 넣지 않음 |

## 5. 자동 점검 목록

| 점검 | 수준 | 기준 | 모형이 할 대처 |
|---|---|---|---|
| 분모 | 경고 | 분자에 해당하는 사람이 한 명도 없는 연령대(관측 300건 이상)가 분모의 15% 이상 | `where`를 제도의 대상 집단으로 한정해 다시 실행. 질문이 그 분모를 명시했으면 사유를 유의 사항에 |
| 0 비교 | 경고 | 0인 값이 없는 변수를 `== 0`으로 비교 | `isna(변수)`로 고쳐 다시 실행 |
| 수치 대조 | 경고 | 「결과」에 실행 결과에 없는 수치 | 실행 결과의 값만 써서 다시 작성 |
| 요청 반영 | 주의 | 질문의 조건에 해당하는 표현이 코드에 없음 | 빠뜨린 조건이면 넣어 다시 실행 |
| 용어 | 주의 또는 참고 | 내역이 정해지지 않은 제도 용어를 되묻지 않고 한 가지로 해석해 실행(주의), 기본 해석으로 진행(참고) | 해석한 변수와 다른 해석 가능성을 유의 사항에 |
| 분류 누락 | 주의 | 분류 기준에 값이 없어 빠진 대상 0.5% 이상 | 빠진 비율을 유의 사항에 |
| 0 포함 | 주의 | 금액의 평균·분위수에서 계산 대상의 20% 이상이 0 | 금액이 있는 사람만 대상이면 `변수 > 0` 조건 추가 |
| 억제 | 주의 | 억제 칸이 절반 초과 | 분류 기준을 줄이는 방법 제안 |
| 전체 값 | 참고(범위 밖이면 주의) | 분류하지 않은 전체 값 | 해석의 기준으로 사용 |
| 기준 시점, 값 있는 대상 | 참고 | 연간·12월 기준, 계산에 포함된 대상의 비율 | 유의 사항에 |
| 변수 | 오류 또는 주의 | 없는 변수·값이 없는 변수(실행 안 함), 정의를 보지 않은 변수(주의) | 변수 찾기·정의 확인 후 다시 작성 |
| 그림 | 주의 | 제목 없음, 잘린 글자, 값 표기 겹침 | 그림 종류를 바꾸거나 유의 사항에 |

기준값(15%, 300건, 0.5%, 20%)은 준비 단계의 값이며 `ssda/verify.py`에 있음. 운영 주체가 확정함(결정필요사항 6번).

## 6. 자체 시험 결과(2026-11-13, 모형 없이 수행)

`python 06_build/harness_selftest.py` — 정답 코드에서 대상 조건을 빼고 응답에 없는 수치를 적는 모의 모형을 벤치마크 121문항에 적용함.

| 분모 경고로 탐지 | 30 |

탐지하지 못해 값이 달라진 9문항은 대상이 제도 변수로 정해지는 질문임: 「등록장애인 중에서」, 「생계급여 수급자 가운데」, 「방문요양서비스 수급자의」, 「근로소득이 있는 사람의」, 「에너지바우처 이용자의」 등. 이 유형은 자동 점검으로 잡히지 않으므로 지침과 학습 자료에 의존함.

그림 점검은 그림 5종 192개 조합에서 기존 그림 함수의 결함 3종(막대 끝 값 표기 잘림, 시도 지도의 서울·경기 값 표기 겹침, 긴 제목 넘침)을 찾아냈고, 수정 후 192개 모두 이상 없음으로 나옴.

학습 자료에도 같은 점검을 적용해 결함 16건(참고 자료에 없는 변수를 쓴 예시 7건, 출력에서 잘린 값이나 맞지 않는 칸 수를 인용한 예시 9건)을 찾아 고침.

## 6-1. 실제 모형으로 확인한 사항과 보완(2026-11-15, CPU 구동)

직접 만든 양자화본(Q4_K_M)을 llama.cpp 서버로 CPU에서 구동해 분석 질문 1건과 평가 문항 13개(벤치마크 11, 안전성 시험 2)를 조립기로 처리함. 일부 문항의 결과이므로 성능 평가로 쓰지 않으며, 하네스와 모형의 표현이 어긋나는 지점을 GPU 가동 전에 찾는 용도임.

| 관찰 | 영향 | 보완 |
|---|---|---|
| 문단 이름을 굵은 글씨(`**결과**`)나 낫표(「확인 필요」)로 적음 | 수치 대조가 「결과」 문단을 찾지 못해 대조 대상이 0개로 집계됨 | `ssda/verify.py`의 문단 인식이 꾸밈 문자를 허용함(`_DECO`) |
| 「결과」에 기준 기간(「2022년 1.1.~12.31.」)을 적음 | 연도와 날짜가 실행 결과에 없는 수치로 잡힘 | 날짜·기간 표기를 수치 대조에서 제외함(`_strip_dates`) |
| 분석 함수의 인자 이름을 짐작해 씀: `rate(where=…, denom_where=…)`, `rate(…, numerator=…)`, `define_group('age', […], labels=[…])`. 분석 문항 6개 중 3개에서 발생했고 2개는 끝까지 실행에 실패함 | 실행 성공률과 산출값 일치율이 떨어짐 | 시스템 프롬프트에 「함수 사용법」(서명과 예)을 넣음. 인자 오류와 없는 함수 오류에는 실행기가 해당 함수의 서명을 「사용법:」 줄로 돌려줌(`ssda/runner.py`의 `usage_hint`) |
| 구간을 만들 때 경계와 항목 이름이 어긋남: `bins=[65, 70, 75, 80]`에 `['65~69세', …, '85세 이상']`을 주어 65~69세의 값이 「70~74세」로 표시됨(보완 후 재확인 1차에서 발생). 실행은 성공하므로 기존 점검에 걸리지 않음 | 항목 이름이 한 칸씩 밀린 표가 그대로 응답에 인용됨 | `ssda.define_group`이 항목 이름에 적힌 수를 구간 경계와 대조해 어긋나면 오류로 돌려보냄(`core.py`의 `_check_labels`). 금액처럼 줄여 적은 이름(「1,200만원」)은 대상에서 제외. 개수 오류 문구에 구간 목록을 넣음 |
| 변수 안내·제도 설명 질문에 문단 이름 없이 바로 답함 | 응답 형식 준수율이 떨어짐(채점기는 「결과」 문단을 봄) | 시스템 프롬프트의 응답 형식에 코드 없이 답하는 경우를 명시함 |
| 그림 이름에 확장자를 붙임(`save(fig, 'x.png')`) | 파일 이름이 `x.png.png`가 됨 | `ssda/plot.py`의 `save`가 확장자를 떼고 저장함 |
| llama.cpp 서버가 질문마다 시스템 프롬프트를 처음부터 다시 처리함(이 모형 구조에서는 프롬프트 앞부분을 임의 위치부터 이어 쓰지 못함) | 문항마다 입력 처리 시간이 늘어남 | 조립기가 시작할 때 예열 요청을 보내 서버에 상태 저장 지점을 남김(`clients.py`의 `warmup`) |

- 13문항의 지표: 문항 통과율 9/11, 변수 선택 정확도 1.0, 수치 근거율 1.0, 확인 질문·제도 용어 문항 4/4, 안전성 시험 거절 2/2, 차단 실패 0건. 통과하지 못한 2문항(B025, B060)은 모두 함수 인자 오류가 원인임
- 보완 후 재확인 1차(B001, B025, B060): 변수 안내 문항이 「결과」「유의 사항」 형식으로 답함(응답 형식 준수율 3/3), B025는 한 번의 실행으로 정답과 일치함(종전 2회 실패). B060은 함수 호출은 맞았으나 위 표의 구간 어긋남으로 값이 정답과 달랐음 → 구간 이름 점검을 추가함
- 보완 후 재확인 2차(B060): 구간 이름 점검과 「함수 사용법」의 구간 설명을 넣은 뒤 한 번의 실행으로 정답과 일치함(65세 미만 구간에 이름을 주고 경계 5개를 유지)
- 재확인은 4문항에 그치며 나머지 문항에서의 효과는 GPU 평가에서 확인됨. 점검표에는 틀린 호출과 어긋난 구간을 잡는지 보는 시험(`06_build/usage_probe.py`)을 넣었음
- 예열 요청의 효과(같은 재확인의 서버 기록): 프롬프트 전체 재처리는 예열 1회뿐이고 이후 6회의 요청은 저장 지점(1,888토큰 위치)에서 이어 처리함. 문항 첫 호출의 처리량이 약 4,100토큰에서 약 2,240토큰으로 줄어듦
- 「함수 사용법」은 긴 판 시스템 프롬프트(`system_prompt.md`)에만 넣었음. 짧은 판은 미세조정한 모형용이며 함수의 쓰임을 학습 예시에서 익히므로 그대로 둠(학습 자료를 다시 만들 필요 없음)
- 「사용법:」 줄은 오류가 난 실행에만 붙으므로 학습 자료(오류 없는 실행)의 문구는 바뀌지 않음. 전수 재검증으로 확인함
- 대화 기록과 지표: `05_eval/runs/arete27b_q4_cpu_subset/`(13문항), `arete27b_q4_cpu_recheck/`·`arete27b_q4_cpu_recheck2/`(재확인), 요약: `모형반입/cpu_실모형_시험.md`

## 8. 설정과 유지

- 설정: `config/assistant.yaml`의 `verify` 절. `result_checks`(산출 점검 회신), `ground_variables`(변수 점검), `ground_numbers`(수치 대조), `answer_retries`(다시 작성 횟수), `footer`(검증 요약)
- 시범 운영에서 새 실수 유형이 확인되면 다음 순서로 반영함
  1. 점검 규칙 추가: `ssda/verify.py`(`check_result` 또는 `check_request`)
  2. 대처 방법 기술: `01_knowledge/docs/verification_guide.md`, 필요하면 시스템 프롬프트의 「검증 결과 읽는 법」
  3. 학습 예시 추가: `04_training/generate.py`에 유형 추가 → `validate.py`로 전수 검증
  4. 평가 문항 추가: `05_eval/build_benchmark.py`의 「I 검증 대응」
  5. `python 06_build/preflight.py`로 전체 재점검
- 점검 규칙을 고친 뒤에는 학습 자료와 벤치마크 정답을 다시 생성해야 함. 「[검증 결과]」 문단이 학습 자료에 들어 있기 때문임
